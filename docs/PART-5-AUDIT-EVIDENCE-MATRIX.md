## Newly reproduced refresh-credential flaw

At baseline, a password or role change increments `users.token_version`, so the old access JWT stops working. However, `refresh_tokens` had no issuance version. `rotateRefreshToken()` accepted the old refresh credential, and the refresh route then read the user's new version and minted a new access JWT. A stolen refresh credential could therefore survive a password change. A role change still used the current DB-derived role; this is a session-revocation bypass, not proof of retaining a removed role.

Two regression cases were saved at `a58d17f992a55c99a7a5fab0330f61e19fa6d0bc`. [Reproduction CI #40750773872](https://github.com/AloneSmoker007/Nova-AI/actions/runs/40750773872) ran against real PostgreSQL 15: the focused suite reported **2 pass / 2 fail**, specifically password-change and role-change refresh renewal. Its later integration steps were skipped after that failure; they are not passing evidence.

### Follow-up behavior and verification contract

- Append migration 035 instead of editing previously applied migrations. Bind each new refresh credential to the account version when issued, preserve that version during rotation, and reject obsolete-version rotation and logout authority before all-session replay revocation.
- Carry the password-verified version from login into refresh issuance. A stale login result cannot acquire a new-version refresh credential.
- Recheck the rotated version against the account in the actual refresh handler before issuing access. This closes the race where credentials change after rotation but before access-token signing.
- Cover legitimate fresh rotation, later credential changes, obsolete-token replay/logout without revoking fresh/other-tenant sessions, expired/forged/cross-tenant/suspended identity rejection, legacy migration behavior, and a deterministic race through the real route handler. The handler test bypasses HTTP/limiter middleware intentionally; it is not a live-provider or full HTTP concurrency test.
- **Upgrade impact:** migration 035 revokes all preexisting refresh credentials because their issuance version cannot be established. Users must sign in again when their current access JWT expires. Existing access JWTs retain their current expiry/version checks. Schedule and communicate this at release; do not silently backfill untrusted credentials with the current account version.
- The expanded PostgreSQL assertions are environment-gated locally. Read the CI run at the commit containing this follow-up before calling the fix verified. Local lint/unit checks alone do not prove the migration or race regression.
